CATEGORY 1: MEMORY BANDWIDTH OPTIMIZATIONS
════════════════════════════════════════════════════════════════

The core problem: We're moving 512 bytes per tile per gate (read
input, write output), but only doing ~256 FLOPs. This is a 2:1
bytes:FLOP ratio, which is TERRIBLE for GPU efficiency.

Strategy 1.1: FUSED GATE OPERATIONS
────────────────────────────────────────────────────────────────
Problem: Each gate requires a memory read/write
Solution: Apply MULTIPLE gates before writing back to memory

Implementation:
  • Load tile into shared memory (512 bytes)
  • Apply gate 1: A = A × G1
  • Apply gate 2: A = A × G2  (NO memory write!)
  • Apply gate 3: A = A × G3  (NO memory write!)
  • Write final result (512 bytes)

Example: 3 fused gates
  • Old: 3 reads + 3 writes = 3072 bytes
  • New: 1 read + 1 write = 1024 bytes
  • Savings: 3× less memory traffic!

Expected speedup: 2-3× (if we fuse 3-4 gates)
Difficulty: MEDIUM (need to precompute G_combined = G1 × G2 × G3)

Strategy 1.2: AMPLITUDE COMPRESSION
────────────────────────────────────────────────────────────────
Problem: We store ALL amplitudes, even tiny ones
Solution: Compress low-probability amplitudes

Implementation:
  • Quantize small amplitudes to zero
  • Use sparse storage for mostly-zero tiles
  • Only process non-zero tiles

Example: After many gates, most amplitudes < 0.001
  • Store 256 amplitudes as: [count, indices[], values[]]
  • Skip WMMA for zero tiles
  • Use custom sparse kernel for partial tiles

Expected speedup: 2-5× (depends on circuit sparsity)
Difficulty: HARD (requires sparse WMMA custom kernel)

Strategy 1.3: TILE BATCHING IN SHARED MEMORY
────────────────────────────────────────────────────────────────
Problem: Each warp processes 1 tile independently
Solution: Load multiple tiles into shared memory, batch process

Implementation:
  • Each block (8 warps) loads 8 tiles to shared memory
  • Process all 8 tiles before writing back
  • Better cache utilization

Expected speedup: 1.2-1.5×
Difficulty: MEDIUM

Strategy 1.4: PREFETCHING WITH ASYNC COPY
────────────────────────────────────────────────────────────────
Problem: Memory latency not fully hidden
Solution: Use CUDA async copy to prefetch next tile

Implementation:
  • While processing tile N, prefetch tile N+1
  • Use cp.async instructions (Ampere+)
  • Double buffering in shared memory

Expected speedup: 1.1-1.3×
Difficulty: MEDIUM

CATEGORY 2: COMPUTE OPTIMIZATIONS
════════════════════════════════════════════════════════════════

Our Tensor Cores are IDLE (<1% utilized). Let's give them work!

Strategy 2.1: INCREASE DEPTH PER KERNEL
────────────────────────────────────────────────────────────────
Problem: We're doing 1M depth per kernel
Solution: Increase to 10M or 100M depth

Why this helps:
  • Amortize kernel launch overhead
  • Better memory access patterns over time
  • More compute per memory transfer

Expected speedup: 1.05-1.1× (diminishing returns)
Difficulty: EASY (just increase depth parameter!)

Strategy 2.2: MULTI-GATE TYPES IN SINGLE KERNEL
────────────────────────────────────────────────────────────────
Problem: Each kernel applies same gate repeatedly
Solution: Pass array of gates, apply sequence

Implementation:
  • gates[depth] array in constant memory
  • Loop: A = A × gates[i]
  • Enables real circuits (not just H^1000000)

Expected speedup: No direct speedup, but enables real workloads
Difficulty: MEDIUM

Strategy 2.3: MIXED PRECISION (FP8 / INT8)
────────────────────────────────────────────────────────────────
Problem: FP16 uses 2 bytes per amplitude
Solution: Use FP8 for some operations, upcast when needed

Implementation:
  • Store amplitudes in FP8 (1 byte)
  • Load to FP16 for WMMA
  • Store back as FP8
  • 2× memory bandwidth reduction!

Expected speedup: 1.5-2× (double the bandwidth!)
Difficulty: HARD (requires H100 for FP8 WMMA, or custom kernels)

Strategy 2.4: GATE MATRIX SPARSITY
────────────────────────────────────────────────────────────────
Problem: WMMA does full 16×16 matmul even for sparse gates
Solution: Custom sparse WMMA for common gates

Example: Pauli-X is a permutation matrix
  • Don't do matmul, just SWAP rows!
  • 16× faster than WMMA for permutations
  • Hadamard is dense (can't optimize much)

Expected speedup: 2-10× for sparse gate sequences
Difficulty: HARD (need custom kernel per gate type)

Strategy 4.2: GATE DECOMPOSITION OPTIMIZATION
────────────────────────────────────────────────────────────────
Problem: Complex gates decompose to many small gates

  • Typical: Decomposes to 6 CNOTs + 9 single-qubit gates

Strategy 4.3: AMPLITUDE CUTOFF / PRUNING
────────────────────────────────────────────────────────────────
Problem: Track amplitudes even when < 10^-6
Solution: Dynamically prune negligible amplitudes

Implementation:
  • After every N gates, scan for tiny amplitudes
  • Zero out anything < threshold
  • Renormalize remaining amplitudes
  • Switch to sparse representation

Expected speedup: 2-10× for deep circuits
Difficulty: MEDIUM

Strategy 4.4: STATEVECTOR COMPRESSION (Schmidt Decomposition)
────────────────────────────────────────────────────────────────
Problem: Store full 2^n statevector even if separable
Solution: Detect separable states, factor representation

Example: |ψ⟩ = |0⟩ ⊗ |1⟩
  • Full: 2^n amplitudes
  • Factored: n separate 2-amp vectors
  • Exponential savings!

Expected speedup: MASSIVE for low-entanglement circuits
Difficulty: VERY HARD (PhD-level quantum algorithms)

CATEGORY 6: WHY TENSOR CORES ARE UNDERUTILIZED
════════════════════════════════════════════════════════════════

Current situation:
  • Tensor Cores: 184 cores, 2.48 GHz
  • Peak FP16: ~1.8 PFLOPS (with sparsity)
  • Our usage: ~5 TFLOPS (0.3%)

Why so low?

REASON 1: MEMORY BANDWIDTH BOUND
────────────────────────────────────────────────────────────────
For each 16×16 WMMA operation:
  • Load A: 512 bytes
  • Load B: 512 bytes (cached after first load)
  • Store C: 512 bytes
  • Total: 1024 bytes per WMMA op

WMMA does:
  • 16×16×16 = 4096 FP16 multiplies
  • 16×16×16 = 4096 FP16 additions
  • Total: 8192 FLOPs

Arithmetic Intensity: 8192 FLOPs / 1024 bytes = 8 FLOP/byte

RTX 4070 specs:
  • Memory bandwidth: 504 GB/s
  • FP16 throughput: 1.8 PFLOPS
  • Required intensity for compute-bound: 1800 TFLOPS / 504 GB/s
    = 3571 FLOP/byte

We need 3571 FLOP/byte, but only have 8 FLOP/byte!
We're 446× too memory-intensive for the hardware balance!

REASON 2: DEPTH IS TOO SHALLOW
────────────────────────────────────────────────────────────────
At depth=1M:
  • Each tile loaded once, processed 1M times
  • Effective intensity: 8 × 1M = 8M FLOP/byte (much better!)

But wait, we're STILL bandwidth bound? Why?

Because we write intermediate results!
  • After each WMMA: write 512 bytes
  • Next WMMA: read 512 bytes again
  • Ping-pong between shared memory buffers
  • This KILLS our intensity!

SOLUTION: Keep results in registers/shared memory longer
  • Don't write after each WMMA
  • Apply multiple gates before writing
  • This is Strategy 1.1 (FUSED GATES)!
